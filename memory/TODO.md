## CI: the gate, the nightly and the two slow checks (built; the last part is a pull request, not merged when this was written)

- **The gate and the nightly are merged (#414, 2026-10-16).** `CI` chooses a lane per pull request (`tools/ci_lanes.py`; `docs/development.md`, "The CI lanes"): docs-only runs Governance and Documentation; code runs lint and tests of the touched packages and their dependents on Ubuntu, plus Windows and macOS when a file holds platform code; build-wide changes, unknown paths or the `full-ci` label run everything. `Nightly` runs everything on `main` each night something merged and opens or updates one `nightly-failure` issue on a failure (stop the line). CI builds tests without debug information (the 23-minute Ubuntu test binary now takes under 3). Measured on #414 (no build cache yet): docs-only 2 min 15 s (was 33 min), one CLI file 3 min 16 s, one domain file 6 min 23 s, the full lane 18 min 55 s (was 34 min), the nightly 20 min 25 s and green. Branch protection already requires `CI result`, `Documentation`, `Governance`, `Dependency policy`, `Dependency review` and `Analyze Rust` (the three `Quality (...)` checks are gone) and the `full-ci` label exists.
- **The two slow checks leave the pull request's path (this change; the maintainer's decision of 2026-10-16).** `Analyze Rust` (CodeQL, required) is one job that always reports: it asks `tools/ci_lanes.py --codeql-only` whether the change touches what CodeQL reads (Rust sources, Cargo manifests and lockfile, `crates/`, `fuzz/`, `.cargo/`, the toolchain file, the CodeQL workflow or configuration) and skips the analysis steps otherwise, so a docs-only pull request gets it in seconds; pushes to `main` and the weekly schedule always analyse. `P14 local upgrade` no longer runs on pull requests: the `Nightly` workflow calls it every night something merged (its failure stops the line), `CI` calls it for a pull request with the `full-ci` label, and it can be dispatched on any ref. A code pull request that needs CodeQL still waits 6 to 8 minutes for it, in parallel with the lane, so it can exceed the 5-minute target and stays under 10.
- **For the weekly window (the supervisor places this in `docs/operations/release.md` 6.18 step 3, which another change owns):** RQ-04's local-registry run is recorded from a dispatch on the candidate's tag, `gh workflow run p14-local-upgrade.yml --repo smormah/vsift --ref v<candidate>` (optional `-f from_version=<published version>`, default `0.1.0`); the build is of the ref, so the ref names the source. ## The test and release model, in one view (decided 2026-10-16; the machinery is not all built)

- **Pull-request gate** (built in #414 and the change after it): only what the change can affect; target 5 minutes, hard limit 10; docs-only runs the document and governance checks; Windows and macOS only for platform-sensitive changes; a hot fix can ask for the full three-system run.
- **Nightly on `main`** when something merged (built in #414; it now includes `P14 local upgrade`): a failure opens an issue and stops development until fixed; **a candidate is cut only from a commit whose nightly passed** (enforced by the Release workflow's `guard` job once the release-workflow change merges).
- **Weekly window:** cut at Friday or Saturday midnight in the maintainer's local time; the long hosted runs follow, for what the week touched; publish on Monday or Tuesday on the maintainer's approval; a failure gets a targeted fix and a rerun of only the failing workflow.
- **Hot fix:** outside the window: the full ~30-minute three-system check, the publish, then the quick checks of the published bytes.
- **Monthly, or with a major change** (a skill rewrite, a re-pin): agent batches 2 and 3, the dependency-quality checks, the full durability campaign. Not weekly; an ordinary week's skill wording change gets the uncounted skill smoke (about $6). The weekly drift runs stay and open an issue on failure.
- **Two limits to remember:** the evidence ledger's scopes are coarse (`crates` is in most items' scope), so "limited to what the week touched" does not alone make the completeness check pass; and the freeze of `release.md` 6.8, which once the release-workflow change merges stops code merges only on the release branch, not on `main`.

## Guardrails

- **The skill** calls the published CLI only; a new public item needs a skill update in the same change (`skill_contract`); its fuzz seed copy (`fuzz/seeds/handoff_check/SKILL.md`) must equal it byte for byte. **New public items** need their `*::ALL` entry, v1 schemas and a human renderer with a snapshot;
  v1 is additive only; a parser of untrusted input needs a fuzz target; npm packages have no scripts.
- **The release seam:** a change to `vsift-release`, `release.yml` or its lint needs a lint rule, a broken-copy mutation test and the shell check; no workflow runs `npm dist-tag`. On the release branch, after a candidate's tag, only the work record, the installation guide and the launcher's README may change until the stable release is published (`release.md` 6.8); `main` is not frozen. A candidate needs a passed nightly on exactly its commit and a tag on its release branch (the `guard` job). `P14 verify release` for a stable release within seven days of its publish.
- **Trials:** a change to the skill, grader, scenarios or settings after a batch's first counted run voids the batch (`freeze check`); a hold-out failure is a finding, never a grader edit; a state file is never edited by hand without a disclosed decision (L-166).
- **Issues:** a failed run is a finding: issue first, then one re-run. No closing keywords ("Fix #n") in a squash title when the issue must stay open (a merge title closed #359 by accident on 2026-10-11).
- **Public text** uses "supported", "stable" and "qualified" only inside registered statements; every change to a quoted sentence updates `public-claims.json`.

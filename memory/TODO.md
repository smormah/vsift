## The test and release model, in one view (decided 2026-10-16; built 2026-10-16 and 17; first full window 2026-10-17 to 18)

- **Pull-request gate:** only what the change can affect (`tools/ci_lanes.py`); target 5 minutes, limit 10; `full-ci` label runs everything.
- **Nightly on `main`** when something merged (02:41 UTC; also by dispatch, on any branch): a failure opens a `nightly-failure` issue and stops the line; **a candidate needs a passed nightly of exactly its commit** (the `guard`).
- **Weekly window:** cut Friday or Saturday midnight (maintainer's local time) on `release/<MAJOR>.<MINOR>.x`; long hosted runs on the tag for what the week touched; publish Monday or Tuesday on the maintainer's approval; `main` keeps taking merges; after the stable publish, the records change to `main` (6.18 step 5, 6.20).
- **The overnight lane (LOKI, since ADR 0025; not yet running):** every night the Windows stress suites on the maintainer's test machine, and `repro` dispatches for load rates; a failure is a finding (`loki-overnight-failure`), not a stopped line, and never release evidence alone. No load runs on a development machine.
- **Hot fix** outside the window: the full nightly on the branch, publish, quick checks. **Monthly or with a major change:** agent batches 2 and 3, the dependency-quality checks, the full durability campaign; an ordinary week's skill wording change gets the uncounted skill smoke.

## Guardrails

- **The skill** calls the published CLI only; a new public item needs a skill update in the same change (`skill_contract`); its fuzz seed copy (`fuzz/seeds/handoff_check/SKILL.md`) must equal it byte for byte. **New public items** need their `*::ALL` entry, v1 schemas and a human renderer with a snapshot; v1 is additive only; a parser of untrusted input needs a fuzz target; npm packages have no scripts.
- **The release branch (6.8):** after a candidate's tag, only fixes for findings change code there, each with a counterpart pull request to `main`; the stable commit differs from the highest `-rc.N` only in version strings, the two shipped documents and the work record (edits and additions, never a deletion or rename). The release seam: a change to `vsift-release`, `release.yml` or its lint needs a lint rule, a broken-copy test and the shell check; no workflow runs `npm dist-tag`. `P14 verify release` for a stable release within seven days of its publish; copy `release-delta.json` into the ledger in the records change (L-103).
- **Trials:** a change to the skill, grader, scenarios or settings after a batch's first counted run voids the batch (`freeze check`); a hold-out failure is a finding, never a grader edit; a state file is never edited by hand without a disclosed decision (L-166).
- **Issues:** a failed run is a finding: issue first, then one re-run. No closing keywords before an issue number that must stay open (#359 on 2026-10-11 and #404 on 2026-10-17 were closed that way).
- **Public text** uses "supported", "stable" and "qualified" only inside registered statements; every change to a quoted sentence updates `public-claims.json`. Every `release` environment gate and every npm write stays with the maintainer.

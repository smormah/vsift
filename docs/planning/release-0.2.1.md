## What this release is, and why

`0.2.0` was published on 2026-10-09 and is what `npm install vsift-cli` installs. The first real recording tried with it, the day after, found a defect that the synthetic recordings of every earlier test could not:
`transcript retranscribe` failed the whole run, kept nothing and said the speech recogniser was missing ([#353](https://github.com/smormah/vsift/issues/353), L-145, high; **loud**, and fixed
on `main`). The maintainer decided on 2026-10-10 that a patch release carries that fix with everything else that was waiting, and the first candidate was cut and published the same evening.

The maintainer's live testing on two real recordings (a 34:36 lecture and a 17:34 spoken walkthrough, on `0.2.0`; findings posted 2026-10-10) then found a **second serious transcription defect, silent**: merging the
overlapping 30-second pieces can drop speech at a seam while the result still says the whole range was transcribed ([#359](https://github.com/smormah/vsift/issues/359), L-149, high; the
cause is inferred from the source and timings, not confirmed with raw recogniser output, and nobody has listened to the audio yet), and a set of findings about how an agent uses the CLI and the skill on a
recording that is more than a few minutes long. **On 2026-10-11 the maintainer decided to put #359 into `0.2.1`, which changes the transcription code, so a second candidate will be cut, and that the larger findings
ride along.** **It is a patch release, not a work packet.** P00 to P14 stay complete, `0.2.0` stays published and is not deprecated, and **`0.2.0` is affected by both L-145 and
L-149 until `0.2.1` is published**: the README and the installation guide carry a known-issue note for each, with the workarounds.

**Decided on 2026-10-13 to go into `0.2.1` (rc.3): the finding from a second machine.** [#391](https://github.com/smormah/vsift/issues/391) ([L-161](known-limits.md#l-161), medium): on a second Windows 11 machine the first `vsift setup check` after a start reported an installed, healthy FFmpeg and FFprobe as `[timeout]`, called the setup `blocked` and advised installing them; the second run said `[ok]`. The three probes share one deadline, which was 5 seconds, and a timeout got the advice of a missing tool. The maintainer's decisions: fix it in `0.2.1`, raise the default, keep one shared deadline, no silent retry. **Built (#392) and in the cut of rc.3:** the default is 30 seconds (the supervisor's proposal, confirmed by the merge); a timed-out tool is told what happened (started and no answer, or not started), under which deadline, and to run the check again or allow more time, in the readable output and in `remediation.next_step`, and is never told to install or locate the tool; in `setup plan` such a probe causes no managed action, and the tool's step says either that the plan proposes nothing because of it or, when the plan installs the paired FFmpeg and FFprobe build because the other tool is missing, that the build replaces it; after `--timeout-seconds 60` the advice no longer offers more time; the published `timed_out`, `blocked` and exit status are unchanged, and no schema changed. **Not shown:** the cold start itself (the tests use stand-in tools that never answer, and `--timeout-seconds 1`); anything on macOS or Linux; that 30 seconds is enough on a slow machine. **The skill is not changed** and does not name `timed_out`. The issue stays open until the released candidate has been run on the machine that showed it.
